# 架构设计

## 1. 进程模型

```
┌─────────────────────────────────────────────────────┐
│  WebView2 窗口（内嵌 HTML/CSS/JS，go:embed）         │
│  加载 http://127.0.0.1:45800/                       │
└──────────────────┬──────────────────────────────────┘
                   │ fetch，每 600ms 轮询 /api/state
┌──────────────────▼──────────────────────────────────┐
│  单一 HTTP Server，监听 0.0.0.0:45800                │
│  ├── /            静态 UI（内嵌）                    │
│  └── /api/*       本机 UI 和局域网对端共用            │
└───────┬─────────────────────────────┬───────────────┘
        │ 发送侧（HTTP client）        │ 接收侧（HTTP handler）
        ▼                             ▼
  POST /api/offer  ──────────▶  hOffer：入队 → 等用户确认 → 建 Session
  POST /api/upload ──────────▶  hUpload：写 .part → 校验字节数 → rename
  POST /api/done   ──────────▶  hDone：结会话，transfer 置 done
```

一个端口同时承担「GUI 的后端」和「局域网对端 API」两个角色。这样 UI 与 API 同源，省掉 CORS 和额外的绑定层；副作用是局域网内任何设备用浏览器打开 `http://<ip>:45800/` 都能看到同样的界面。

## 2. 发现

| 通道 | 参数 | 频率 | 作用 |
|---|---|---|---|
| UDP 组播 | `239.255.72.89:45800`，JSON announce | 1.5 s | 主通道，双向 |
| /24 扫描 | `GET /api/info`，300 ms 超时，128 并发 | 60 s | 兜底，应对 AP 隔离 / 禁 IGMP |

`announceMsg`：`{t:"hi"|"bye", id, name, port, os}`。

对端地址取 **UDP 包的源 IP**，不信任报文里自报的地址。设备表按 `id` 索引，7 秒没心跳就移除（4 个周期）。

**Windows 特有坑**：`net.ListenMulticastUDP` 会 bind 到组播地址本身，Windows 接受 bind 但永不投递数据。必须 `syscall.Socket` 手建、`SO_REUSEADDR` 先于 bind、bind `INADDR_ANY`、再逐网卡 `IP_ADD_MEMBERSHIP`。见 `mcast_windows.go`。

## 3. 传输协议

```
发送方                                   接收方
  │                                        │
  │ POST /api/offer                        │
  │ {from:{id,name}, files:[{name,size}]}  │
  │ ──────────────────────────────────────▶│ 入队（上限 8）
  │                                        │ 用户点「接收」
  │◀────────────────────────────────────── │ 200 {session}
  │                                        │
  │ POST /api/upload?session=&idx=         │
  │ <裸二进制，Content-Length=size>         │
  │ ──────────────────────────────────────▶│ .part → rename
  │◀────────────────────────────────────── │ 200
  │  （对每个文件重复，串行）                 │
  │                                        │
  │ POST /api/done?session=                │
  │ ──────────────────────────────────────▶│ transfer=done
```

**为什么一个文件一个请求**：中断只需重传当前文件，进度粒度天然对齐；并行多文件在千兆网上只会加剧接收端磁盘竞争。

**为什么用 HTTP 而不是裸 TCP**：调试可直接 curl；未来加 `Content-Range` 断点续传零成本；Go 标准库的 `io.Copy` 在 Windows 上走 `sendfile`/`TransmitFile` 路径。

**为什么不校验 sha256**：v0.1 只按字节数比对。加哈希要读两遍文件（发送端）或额外算一遍（接收端），在 110 MB/s 的链路上得不偿失——除非后续做秒传。

### 3.1 拖拽发送：为什么数据要绕一圈

浏览器不暴露本地文件的真实路径（`<input type=file>` 和拖放都一样）。机器上没装 WebView2 时会退回 Edge 窗口，那种情况下连 Win32 的 `WM_DROPFILES` 都够不着——窗口是独立的浏览器进程，不是我们的。

所以拖拽走的是唯一在两种窗口模式下都成立的路径：

```
页面 File 对象 ──fetch(POST body)──▶ 本机 Go 进程 ──HTTP──▶ 对端
```

| 接口 | 作用 |
|---|---|
| `POST /api/drop-prepare` | 复用同一套 offer 协商，返回 job id；对方拒绝时这里就返回失败 |
| `POST /api/drop-file?job=&idx=` | 请求体即文件字节，`progressReader` 直连对端 upload |
| `POST /api/drop-done?job=` | 发 `/api/done` 收尾，transfer 置 done |

**不落盘、不整体缓冲**：整个链路只占一个 32 KB 拷贝缓冲，10 GB 文件的内存占用和 10 KB 一样。代价是数据在回环接口上多走一跳（Chromium 读盘 → 本地 HTTP → 对端），但回环吞吐远高于千兆的 110 MB/s，实测不是瓶颈。

**三个接口都只接受 127.0.0.1**：否则局域网内任何设备都能 POST 一个文件，让本机替它把数据转发出去。

**为什么不用 `AllowExternalDrop=false` + 窗口子类化拿真路径**：那需要手工按 COM vtable 偏移调用 `ICoreWebView2Controller4`，与库内部结构强耦合；而且降级到 Edge 窗口后完全失效。为了省一次回环拷贝引入两种实现路径，不划算。

## 4. 并发模型

| 维度 | 行为 |
|---|---|
| 多设备发现 | `peers map[string]*Peer` + 一把 `sync.Mutex` |
| 多入站请求 | `offer []*PendingOffer` 队列，每个请求一个 goroutine 阻塞在 `select{ch, timeout, ctx.Done()}` |
| 多会话 | `sessions map[string]*Session`，各 session 独立目录，可并发写 |
| 多出站 | 每次点击起一个 `doSend` goroutine，互不阻塞 |
| 进度更新 | `addProgress` 持锁累加，速度用 EMA（0.65 旧 + 0.35 新）平滑 |

无锁粒度的优化没必要：所有共享状态都是几十字节的结构体，锁竞争远低于磁盘和网络。

### 4.1 多设备时"发给谁"

拖拽的落点由**光标位置**决定，不看设备名：`elementFromPoint(x, y).closest('.peer')` 取到卡片，再取 `data-id`。所以 N 台设备时，文件只会发往松开鼠标的那一张卡片，不需要任何"当前选中设备"的状态。

多台设备时拖到空白处**拒绝发送**并提示"请把文件拖到某个设备卡片上"——宁可多一步，也不替用户猜。只有当可见设备恰好 1 台时，空白处落点才等价于那一台。

**同名设备**是办公室的常态（都保留 Windows 默认名）。服务端在组装 `/api/state` 时补两个字段：

| 字段 | 规则 |
|---|---|
| `label` | 名字唯一 → 原样；同名 → `名字 (IP)`；名字和 IP 都相同 → `名字 (IP:端口)` |
| `addrLabel` | 卡片第三行：唯一或仅 IP 冲突时显示 `IP`，二者都冲突时显示 `IP:端口` |

拖拽遮罩的标题和传输记录的 `peer` 都用 `label`，所以悬停传输行能看出"发给谁"，不会因为两台机器同名而分不清。最后一级退回端口，是因为同一台机器跑多个实例（或 NAT 后共享 IP）时，只有端口能区分。

## 5. 生命周期与回收

```
PendingOffer ──接受──▶ Session ──每个文件开始时刷新 Deadline──▶ hDone 删除
     │                    │
     └─ 60s 无人应答 ─────┘
           ▼              └─ 5min 无上传 ──▶ janitor 删除 + transfer 置 canceled
        408 超时
```

`janitorLoop` 每 2 秒跑一次，同时负责 peer 过期（7 s）和 session 过期（5 min）。

## 6. 文件落盘

```
<RecvDir>/<文件名>
```

文件直接落在接收目录，不按发送者建子目录——每次传输留一个文件夹在实际使用里只是噪音。

- 文件名由 `createUnique` 预留：先 `os.Stat` 跳过已存在的成品名，再用 `O_EXCL` 建 `<文件名>.part`。**并发上传同名文件时只有一方能拿到 `x.part`，另一方顺延到 `x (1)`**，因此不需要每次传输独立目录也不会互相覆盖。
- 文件名经 `cleanName`：替换 `< > : " / \ | ? *` 和控制字符、修剪首尾点和空格、规避 `CON/PRN/AUX/NUL/COM1-9/LPT1-9`、超 180 字符截断但保留扩展名。
- 先写 `.part`，字节数核对通过后 `os.Rename`。

## 7. 便携性

| 项 | 位置 | 回退 |
|---|---|---|
| 配置 | exe 同目录 `lantransfer.json` | `%APPDATA%\gq\config.json` |
| 日志 | exe 同目录 `lantransfer.log` | 同上目录 |
| WebView2 数据 | `%LOCALAPPDATA%\gq\webview2`（固定） | — |
| 接收目录 | `%USERPROFILE%\Downloads\gq` | 接收弹窗或顶栏可改，切换前校验可写 |

配置写入用「临时文件 + rename」，避免断电写坏。

### 7.1 窗口模式与降级诊断

UI 有两种承载方式，差别只是外壳：

| 模式 | 条件 | 外壳 |
|---|---|---|
| `webview2` | 系统有可用的 WebView2 Runtime | 原生窗口，标题 `gq` |
| `browser` | Runtime 缺失或初始化失败 | Edge/Chrome `--app=` 窗口，无地址栏和标签页 |

`/api/state` 的 `self.window` + `self.windowNote` 把当前模式和原因交给页面，页面顶部据此显示一条可关闭的说明条。这个信息以前只写日志，用户只会看到"打开了个 Edge"，无法判断是程序问题还是环境问题。

失败时按以下顺序取最具体的原因：

1. **注册表与磁盘不一致**：注册表登记了版本，但 `EdgeWebView\Application` 下没有任何 `msedgewebview2.exe`。这是 `0x80070002` 的典型成因（克隆镜像、手工删目录、Edge 自动更新后旧目录被清），且比错误码更能说明问题，所以排在最前；
2. 读回自己日志尾部（`windowsgui` 没有控制台），匹配库打印的 `Result: 80xxxxxx` 或 `Error calling Webview2Loader`，把 HRESULT 翻成中文；
3. 用 `golang.org/x/sys/windows/registry` 直接查 `EdgeUpdate\Clients\{F3017226-...}` 的 `pv`（HKLM/HKCU × 64/32 位视图）。**不走 `reg.exe`**：部分机器用执行策略禁用外部命令，届时探测会静默返回空；
4. 都没有 → "WebView2 初始化失败"。

第 1 步的检查是"有没有任意一个版本目录带 exe"，而不是"注册表版本号对应的目录在不在"：`pv` 可能落后于实际安装（Edge 自动更新只改目录不改这个值），按版本号硬核对会误报。

`DataPath` 显式指向 `%LOCALAPPDATA%\gq\webview2`：库的默认值是 `%APPDATA%\<exe名>`，在漫游配置被重定向、只读或缺失的账户上会创建失败，表现为"什么都没发生，直接开了浏览器"。

### 7.2 防火墙放行：为什么只能靠提权

入站规则是管理员操作，没有用户态替代方案：任何进程都无法绕过 UAC 给自己开入站。收发双方至少有一端要接受连接，所以"改成客户端拉取"也绕不开（拉取方连接对端，对端同样需要入站）。

实现分两个进程：

| 进程 | 做什么 |
|---|---|
| 主进程（非提权） | `POST /api/firewall` → `ShellExecuteW("runas", 自身, "--allow-firewall")`，立即返回；随后页面轮询 `/api/firewall-status` |
| 提权子进程 | `lantransfer.exe --allow-firewall`：先删同名旧规则，再 `netsh` 加 TCP/UDP 两条入站规则，`remoteip=localsubnet` |

要点：

- **用 `ShellExecuteW runas`** 而不是 `exec.Command`：后者不会弹 UAC，只会拿到 ERROR_ELEVATION_REQUIRED。
- **子进程是同一个 exe 的另一个参数**，不额外分发脚本，也不依赖 `powershell.exe`（本机 `reg.exe` 曾被安全策略拦过；`netsh` 实测可用）。
- **状态查询走 `netsh show`**：只读、无需提权、几十毫秒。返回码 0 = 规则存在，页面据此把按钮显示成绿色"已放行"，不靠记忆猜。
- **提权前先检查 token**（`windows.GetCurrentProcessToken().IsElevated()`），未提权直接给一句明确日志，避免把 netsh 的 GBK 输出（会变成乱码）写进 UTF-8 日志。
- **`remoteip=localsubnet`**：文件互传只发生在局域网内，限定来源网段等于零成本收窄授权面。
