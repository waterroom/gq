# 架构设计

## 1. 进程模型

```
┌─────────────────────────────────────────────────────┐
│  WebView2 窗口（内嵌 HTML/CSS/JS，go:embed）         │
│  加载 http://127.0.0.1:45800/                       │
└──────────────────┬──────────────────────────────────┘
                   │ fetch，每 600ms 轮询 /api/state
┌──────────────────▼──────────────────────────────────┐
│  单一 HTTP Server，监听 0.0.0.0:45800                │
│  ├── /            静态 UI（内嵌）                    │
│  └── /api/*       本机 UI 和局域网对端共用            │
└───────┬─────────────────────────────┬───────────────┘
        │ 发送侧（HTTP client）        │ 接收侧（HTTP handler）
        ▼                             ▼
  POST /api/offer  ──────────▶  hOffer：入队 → 等用户确认 → 建 Session
  POST /api/upload ──────────▶  hUpload：写 .part → 校验字节数 → rename
  POST /api/done   ──────────▶  hDone：结会话，transfer 置 done
```

一个端口同时承担「GUI 的后端」和「局域网对端 API」两个角色。这样 UI 与 API 同源，省掉 CORS 和额外的绑定层；副作用是局域网内任何设备用浏览器打开 `http://<ip>:45800/` 都能看到同样的界面。

## 2. 发现

| 通道 | 参数 | 频率 | 作用 |
|---|---|---|---|
| UDP 组播 | `239.255.72.89:45800`，JSON announce | 1.5 s | 主通道，双向 |
| /24 扫描 | `GET /api/info`，300 ms 超时，128 并发 | 60 s | 兜底，应对 AP 隔离 / 禁 IGMP |

`announceMsg`：`{t:"hi"|"bye", id, name, port, os}`。

对端地址取 **UDP 包的源 IP**，不信任报文里自报的地址。设备表按 `id` 索引，7 秒没心跳就移除（4 个周期）。

**Windows 特有坑**：`net.ListenMulticastUDP` 会 bind 到组播地址本身，Windows 接受 bind 但永不投递数据。必须 `syscall.Socket` 手建、`SO_REUSEADDR` 先于 bind、bind `INADDR_ANY`、再逐网卡 `IP_ADD_MEMBERSHIP`。见 `mcast_windows.go`。

## 3. 传输协议

```
发送方                                   接收方
  │                                        │
  │ POST /api/offer                        │
  │ {from:{id,name}, files:[{name,size}]}  │
  │ ──────────────────────────────────────▶│ 入队（上限 8）
  │                                        │ 用户点「接收」
  │◀────────────────────────────────────── │ 200 {session}
  │                                        │
  │ POST /api/upload?session=&idx=         │
  │ <裸二进制，Content-Length=size>         │
  │ ──────────────────────────────────────▶│ .part → rename
  │◀────────────────────────────────────── │ 200
  │  （对每个文件重复，串行）                 │
  │                                        │
  │ POST /api/done?session=                │
  │ ──────────────────────────────────────▶│ transfer=done
```

**为什么一个文件一个请求**：中断只需重传当前文件，进度粒度天然对齐；并行多文件在千兆网上只会加剧接收端磁盘竞争。

**为什么用 HTTP 而不是裸 TCP**：调试可直接 curl；未来加 `Content-Range` 断点续传零成本；Go 标准库的 `io.Copy` 在 Windows 上走 `sendfile`/`TransmitFile` 路径。

**为什么不校验 sha256**：v0.1 只按字节数比对。加哈希要读两遍文件（发送端）或额外算一遍（接收端），在 110 MB/s 的链路上得不偿失——除非后续做秒传。

## 4. 并发模型

| 维度 | 行为 |
|---|---|
| 多设备发现 | `peers map[string]*Peer` + 一把 `sync.Mutex` |
| 多入站请求 | `offer []*PendingOffer` 队列，每个请求一个 goroutine 阻塞在 `select{ch, timeout, ctx.Done()}` |
| 多会话 | `sessions map[string]*Session`，各 session 独立目录，可并发写 |
| 多出站 | 每次点击起一个 `doSend` goroutine，互不阻塞 |
| 进度更新 | `addProgress` 持锁累加，速度用 EMA（0.65 旧 + 0.35 新）平滑 |

无锁粒度的优化没必要：所有共享状态都是几十字节的结构体，锁竞争远低于磁盘和网络。

## 5. 生命周期与回收

```
PendingOffer ──接受──▶ Session ──每个文件开始时刷新 Deadline──▶ hDone 删除
     │                    │
     └─ 60s 无人应答 ─────┘
           ▼              └─ 5min 无上传 ──▶ janitor 删除 + transfer 置 canceled
        408 超时
```

`janitorLoop` 每 2 秒跑一次，同时负责 peer 过期（7 s）和 session 过期（5 min）。

## 6. 文件落盘

```
<RecvDir>/<发送者名>_<月日-时分秒>[-n]/<文件名>
```

- 目录名做 `uniqueDir`，防止同一发送者同一秒发两次混在一起。
- 文件名经 `cleanName`：替换 `< > : " / \ | ? *` 和控制字符、修剪首尾点和空格、规避 `CON/PRN/AUX/NUL/COM1-9/LPT1-9`、超 180 字符截断但保留扩展名。
- 先写 `.part`，字节数核对通过后 `os.Rename`。重名走 `uniquePath` 加 ` (1)`。

## 7. 便携性

| 项 | 位置 | 回退 |
|---|---|---|
| 配置 | exe 同目录 `lantransfer.json` | `%APPDATA%\gq\config.json` |
| 日志 | exe 同目录 `lantransfer.log` | 同上目录 |
| 接收目录 | `%USERPROFILE%\Downloads\gq` | 可在 UI 改 |

配置写入用「临时文件 + rename」，避免断电写坏。
